<Note>
  Git & GitHub worktrees are a preview feature and are enabled by default. Set
  `KATA_FEATURE_GIT_WORKSPACE_V1=0` on the workspace-owning machine to disable
  them. Named Worktree V2 is opt-in: set `KATA_FEATURE_WORKTREE_V2=1` on the
  workspace-owning server, and keep V1 enabled, to show the naming and root
  settings controls.
</Note>

When a session's working directory is inside an existing Git repository, Kata
Agents can give that session its own **managed worktree** — an isolated
checkout on a temporary branch — so the agent's work stays separate from your
current checkout. Creating a workspace or session does not initialize or
publish a repository. You can review the changes and commit, pull, push, or
open a GitHub pull request without leaving the app.

## Where Git runs

Git, worktree, and `gh` commands always run on the **server that owns the
workspace filesystem**. For a local workspace that is your own machine; for a
remote/headless workspace it is the remote server. The desktop app and CLI are
thin clients — they never run Git against your repository directly, and the same
controls appear whether the workspace is local or remote.

**Requirements on the workspace-owning machine:**

- a working `git` client for repository, worktree, commit, pull, and push actions;
- for pull-request actions, the [GitHub CLI (`gh`)](https://cli.github.com/)
  installed **and** authenticated (`gh auth login`).

If Git, a remote, or `gh` is missing, the app shows actionable setup guidance
instead of the action — it never changes your repository state to work around a
missing tool.

## Choosing a workspace for a session

Before the first message in a Git repository, the composer offers a **Workspace**
control:

<Steps>
  <Step title="Current checkout">
    The session works directly in your existing checkout and branch.
  </Step>
  <Step title="New worktree">
    Pick a base ref (defaults to the current branch). With Worktree V2 enabled,
    you can edit the generated name before creating the checkout. Kata uses the
    exact name as the suffix of a `kata-agent/<name>` branch and adds a random
    internal ID to the filesystem leaf. Without V2, it retains the generated
    eight-hex `kata-agent/<id>` branch behavior. The worktree starts from
    committed state — uncommitted changes in your current checkout are not
    copied.
  </Step>
</Steps>

Once a worktree is prepared, the session is locked to it. Restarting or resuming
the session keeps the same worktree — it never silently falls back to your
current checkout.

## Worktree V2 names and roots

Worktree V2 is controlled by the workspace-owning server, not by the desktop
client. In **Settings → Worktrees**, select a capable local or connected server
to view and change its Worktree root. The page labels remote roots with
their server identity; a local directory picker is available only for the local
server.

The default Worktree root is `<CONFIG_DIR>/worktrees`. A saved absolute root (or
`~/…` path) is canonicalized and validated by the owning server before it is stored.
It cannot overlap server configuration, snapshot storage, a registered
repository, or an existing managed checkout. A root change affects only new
worktrees; every existing checkout retains the canonical root recorded when it
was created. The fixed registry remains at
`<CONFIG_DIR>/worktrees/registry.json`, independently of the selected
Worktree root.

Names are branch suffixes, not filesystem paths. In the composer, uppercase
letters, spaces, and underscores are normalized to lowercase kebab-case before
the request is sent—for example, `My New Feature` becomes
`my-new-feature`. Empty names and names that remain Git-invalid, occupied, or
case-colliding are rejected without changing the repository. Nested valid names
such as `team/auth-refresh` are allowed. If a request fails after creating a
branch, the server removes it only when it can prove that the failed transaction
still owns the original branch OID.

## Worktree root and managed worktrees

In **Settings → Worktrees**, select the server that owns the workspace files. The
root setting is labeled **Worktree root** with the description **Directory where
Kata Agents creates managed worktrees**. Changing it affects only new
worktrees; existing checkouts stay where they were created.

The **Managed worktrees** list intentionally stays simple. Each active worktree
shows its name, branch, server path, and one **Delete** button. After a worktree
is deleted, it disappears from the active list. Lifecycle recovery data remains
server-side rather than adding restore, archive, retry, or snapshot controls to
this list.

Deletion still uses a fresh server-side inspection and snapshot-first removal so
Kata Agents can fail safely if the checkout changes while it is being deleted.
The local branch is retained, and snapshots stay on the owning server for
lifecycle recovery; snapshot payload bytes never leave that server.

## Automatic deletion

Automatic deletion is **off by default**.

- **Automatically delete old worktrees** — Recommended for most users. Turn this off only if you want to manage old worktrees and disk usage yourself.
- **Auto-delete limit** — Number of managed worktrees to keep before older ones are pruned automatically. Kata Agents snapshots worktrees before deleting, so pruned worktrees should always be restorable.

The limit is configurable from 1–1000 per server and counts materialized
worktrees only. Cleanup is event-driven; it does not run a background daemon or
use age or disk-size policies. Active or otherwise protected worktrees are
skipped, and in-flight removals complete their journaled transaction.

## Reviewing and sharing work

The Changes panel and the header Git control show the worktree's status and let
you:

- **Commit** selected files with a message;
- **Pull** (fast-forward only);
- **Push**, creating upstream tracking when needed;
- **Create / View pull request** for GitHub remotes when `gh` is ready. New PRs
  target the worktree's base ref and open with an editable title and body.

<Warning>
  V1 is intentionally conservative. It never force-pushes, resets history or your
  working tree, rebases, merges, or auto-resolves conflicts. If a repository is
  mid-merge or has unresolved conflicts, committing is blocked — resolve or abort
  the operation outside Kata first.
</Warning>

## Recovery states

Kata never silently switches your directory. If a managed worktree is moved or
removed outside the app, or its branch is switched externally, the composer badge
shows a visible **recovery** or **blocked** state and Git actions are refused
until you restore the expected branch or delete the session.

## Archiving and deleting sessions

- **Archiving** a session never removes its worktree, but with Worktree V2 the
  archived session's claim is recorded: when **every** owner of a worktree is
  archived (and none is active), the worktree is removed snapshot-first and its
  recovery data remains on the owning server.
- **Deleting** a session drops that session's claim on the worktree but does not
  remove the checkout on its own (the final-owner deletion leaves the worktree
  `unowned` and schedules it for automatic cleanup). Removing the managed
  worktree is a separate, explicit choice in the delete dialog. It is blocked
  while another session still shares the worktree, and removing a worktree with
  uncommitted or unpushed work requires an extra destructive confirmation that
  names what would be lost. With Worktree V2, **Delete session and worktree**
  captures a verified snapshot first and restores the session if removal fails;
  the local branch is always retained. Without V2, the temporary branch is
  pruned only when it has no unique work.
